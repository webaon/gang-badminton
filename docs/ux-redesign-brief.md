# UX/UI Redesign Brief — Gang Badminton

> เอกสาร handoff สำหรับ **Agent ออกแบบ UX/UI ใหม่ทั้งหมด**
> รวบรวมจากโค้ดจริง ณ v1.0.0+ (ถึง PR #13) — ทุกหน้า ทุกความสามารถ ทุกสิทธิ์ ตรงกับที่ deploy อยู่บน production
> Production: https://gang-badminton.vercel.app · Stack: Next.js 16 App Router + Supabase + Astryx + Tailwind v4

---

## 1. ระบบคืออะไร

**แพลตฟอร์ม SaaS จัดการก๊วนแบดมินตัน (multi-tenant)** — หัวหน้าก๊วนเปิดก๊วน บริหารนัดเล่น
รับลงชื่อ+waitlist เช็คอินด้วย QR จัดเกมลงคอร์ท นับลูกแบด ปิดรอบคิดเงินอัตโนมัติ
รับสลิป PromptPay ตรวจยอดค้าง ดูสถิติ/รายงาน และแจ้งเตือนผ่าน LINE OA (ต่อก๊วน, optional)

โครงสร้าง tenant: **Organization → Gang (ก๊วน) → Session (นัดเล่น)**
คนเดียวดูแลหลายก๊วนได้ (เช่น คลับเดียวมีก๊วนจันทร์/พุธ/เสาร์)

## 2. ผู้ใช้ / บทบาท (Personas)

| บทบาท | คือใคร | ทำอะไรได้ (สรุป) |
|---|---|---|
| **Visitor** | คนทั่วไป ยังไม่ login | ดู landing, ค้นหาก๊วน public, ลงชื่อเข้านัดผ่านลิงก์เชิญ |
| **Guest** | ผู้เล่นขาจร **ไม่มี account** | ลงชื่อผ่านลิงก์เชิญ (ชื่อ+เบอร์), ดูสถานะ/ยกเลิกผ่านลิงก์ลับของตัวเอง, claim เป็นสมาชิกภายหลัง |
| **Member** | สมาชิกก๊วน (มี account) | ลงชื่อ/ยกเลิกของตัวเอง, จ่ายเงิน+ส่งสลิป, ดูประกาศ/สถิติ/แจ้งเตือน, ผูก LINE |
| **Admin** | แอดมินก๊วน | ทุกอย่างของ member + สร้าง/จัดการนัด, เช็คอิน, จัดเกม, ปิดรอบคิดเงิน, ตรวจสลิป, จัดการสมาชิก/ราคา/ประกาศ/คำขอเข้าก๊วน, ตั้งค่า LINE, ดูรายงานการเงิน |
| **Owner** | เจ้าของก๊วน | = admin (สิทธิ์เชิงเจ้าของยังไม่มีใน scope ปัจจุบัน) |
| **Org admin** | แอดมินองค์กรที่เป็นเจ้าของก๊วน | นับเป็น admin ของทุกก๊วนใน org อัตโนมัติ |

**บริบทการใช้งานสำคัญต่อการออกแบบ:**
- หน้างานจริงคือ **มือถือข้างคอร์ท** — เหงื่อออก มือไม่ว่าง แสงจ้า ⇒ mobile-first, ปุ่มใหญ่, งานหลักจบในแตะน้อยครั้ง
- หน้า Game Console / สแกนเช็คอิน ใช้ต่อเนื่องตลอดค่ำ ⇒ ต้องอัปเดตเรียลไทม์ อ่านง่ายจากระยะไกล
- Guest เข้าผ่านลิงก์ใน LINE/แชท ⇒ หน้า guest ต้องเบา ไม่บังคับ login ไม่มี navigation รก

| `/` | **Landing** | หน้าการตลาด: จุดขาย "เปิดนัด · ลงชื่อ · คิวอัตโนมัติ · เงินไม่ตกหล่น", CTA สมัคร/เข้าสู่ระบบ |
| `/sign-in` | เข้าสู่ระบบ | อีเมล+รหัสผ่าน หรือ magic link |

| `/join/[token]` | **ลงชื่อผ่านลิงก์เชิญ** | จุดเข้า guest: เห็นข้อมูลนัด (วัน เวลา สถานที่ ที่ว่าง) → กรอกชื่อ+เบอร์ลงชื่อ ไม่ต้องมี account → ได้ลิงก์ลับส่วนตัว; สมาชิกที่ login แล้วลงชื่อตัวเองได้จากหน้านี้เช่นกัน |
| `/guest/[registrationId]` | **สถานะของ guest** | เข้าด้วยลิงก์ลับ: สถานะ (ยืนยัน/waitlist), ยอดต้องจ่าย+QR หลังปิดรอบ, ปุ่มยกเลิก, ปุ่ม **claim** ผูกเป็นบัญชีสมาชิก |

|---|---|---|

| `sessions/[id]/pay` | **จ่ายเงิน** | ยอดของฉัน, **PromptPay QR** (ยอดฝังในภาพ), อัปโหลดสลิป, สถานะตรวจ (รอ/ผ่าน/ตีกลับ→ส่งใหม่) |
| `sessions/[id]/close` | **ปิดรอบคิดเงิน** [admin] | preview ยอดรายคน (ค่าคอร์ท+ค่าลูก ตามแผนราคา ณ วันสร้างนัด) → ยืนยันปิดรอบ = commit ยอดจริง |
| `templates` | ตารางประจำ [admin] | template นัดประจำ (เช่น อังคาร 18:00, 4 คอร์ท 20 คน), เปิด/พักใช้งาน, **สร้างนัดจาก template คลิกเดียว** (cron สร้างล่วงหน้าอัตโนมัติด้วย) |
| `members` | สมาชิก | รายชื่อ+role+ระดับฝีมือ; [admin] เพิ่มด้วยอีเมล, เปลี่ยน role, ถอดออก, ตั้งสมาชิกรายเดือน |
| `join-requests` | คำขอเข้าก๊วน [admin, flag discovery] | คิวคำขอจากหน้าค้นหา → อนุมัติ/ปฏิเสธ |
| `announcements` | ประกาศ | อ่านประกาศ (+รูป); [admin] สร้าง/แก้/ลบ/เผยแพร่, แนบรูป |

| `membership` | บิลรายเดือน [admin] | สมาชิกรายเดือน, **ออกบิลเดือนนี้** (idempotent), สถานะจ่าย |
| `reports` | รายงาน [admin] | รายรับ-รายจ่าย: เก็บได้จริง / ค้างเก็บ / กำไร (netCash), บันทึกรายรับ-รายจ่ายอื่น (ค่าคอร์ท ค่าลูก ฯลฯ), timeline รายวัน |

| `line` | ผูก LINE ของฉัน [flag line] | ขอโค้ดผูกบัญชี LINE, สถานะการผูก, เลิกผูก |
| `liff` | LIFF (เปิดในแอป LINE) | มุมมองย่อในแอป LINE: นัดที่กำลังมาถึง + ลงชื่อเร็ว |

## 5. ความสามารถทั้งหมด (Capability inventory — จาก server actions จริง)

### บัญชี / โปรไฟล์
สมัคร (รหัสผ่าน), เข้าสู่ระบบ (รหัสผ่าน / magic link), ออกจากระบบ, แก้โปรไฟล์

### ก๊วน
สร้างก๊วน (พร้อม org), แก้ตั้งค่า+flags, ค้นหาก๊วน public, ขอเข้าก๊วน / ยกเลิกคำขอ / อนุมัติ-ปฏิเสธ

### สมาชิก
เพิ่มด้วยอีเมล, เปลี่ยน role, ถอดออก, จัดการระดับฝีมือ (เพิ่ม/ลบ scale), ตั้ง/ยกเลิกสมาชิกรายเดือน

### นัดเล่น
สร้าง/แก้นัด, เปลี่ยนสถานะตาม state machine, template (สร้าง/แก้/เปิดปิด/generate ทันที), ลิงก์เชิญ (สร้าง, จำกัดโควต้า)

### การลงชื่อ
ลงชื่อตัวเอง / แทนสมาชิกอื่น / เพิ่ม guest, ยกเลิก (ตัวเอง/แทน/guest — คิด penalty ตาม policy),
**waitlist อัตโนมัติเมื่อเต็ม + เลื่อนคิวอัตโนมัติเมื่อมีที่ว่าง** (เรียงตามคิว+ความน่าเชื่อถือ),
เช็คอิน: QR ของผู้เล่น → admin สแกน, เช็คอินรายคน, เช็คอินทั้งหมด, mark no-show

### เกม (Game Console)
generate จัดเกมอัตโนมัติ (สมดุลฝีมือ + เลี่ยงคู่ซ้ำ), จบเกม, แก้จำนวนลูกที่ใช้, เปลี่ยนตัวผู้เล่น

### เงิน
preview ยอดก่อนปิดรอบ → ปิดรอบ commit ยอด (atomic จุดเดียว), แผนราคา 3 แบบ (เหมาจ่าย / ค่าคอร์ทหาร+ค่าลูก / รายเดือน — สมาชิกรายเดือนไม่หารค่าคอร์ท), ออกบิลรายเดือน (idempotent),
PromptPay QR ยอดฝังในภาพ, ส่งสลิป (guest ก็ส่งได้), verify/reject + ส่งสลิปใหม่ได้, ปรับยอดหลัง verify, ledger ยอดค้างรายคน, บันทึกรายรับ-รายจ่ายอื่น, รายงาน + สถิติ (recompute ได้)

### สื่อสาร
ประกาศ (+รูป), แจ้งเตือน in-app (คิวส่งจริงเบื้องหลัง), LINE: ตั้งค่า OA ต่อก๊วน + quota + ทดสอบ, สมาชิกผูก/เลิกผูกบัญชี, LINE Login, LIFF, reminder ก่อนนัดอัตโนมัติ

## 6. สถานะ (State machines) — UI ต้องออกแบบรองรับทุกสถานะ

```
Session:      draft → open → in_play → billing → settled → archived
              (+ draft/open/in_play → cancelled, open → billing)
Registration: confirmed → checked_in | cancelled | no_show
              waitlist → confirmed (เลื่อนคิวอัตโนมัติเท่านั้น) | cancelled
Payment:      pending → submitted → verified | rejected → submitted (ส่งใหม่ได้)
```

- **"เต็ม" ไม่ใช่สถานะ** — คำนวณจาก `confirmed ≥ max_players` เสมอ (ป้ายบอกที่ว่างต้อง live)
- แต่ละสถานะ session เปลี่ยนว่าใครทำอะไรได้ (เช่น ลงชื่อได้เฉพาะ `open`, จ่ายเงินหลัง `billing`)

### นิยามการเงินที่ตรึงไว้ (หน้าจอห้ามนิยามเอง)
- **เก็บได้จริง** = ยอดจากสลิป verified หัก refund · **กำไร** = เก็บได้จริง + รายรับอื่น − รายจ่าย
- "ค้างเก็บ" กับ "ต้องคืน" แสดงแยกกัน **ไม่หักกลบ**
- ยอดค้างมาจาก ledger ไม่ใช่สถานะสลิป

## 7. ข้อจำกัดทางเทคนิคที่งานออกแบบต้องอยู่ในกรอบ

1. **Design system = Astryx v0.3.0 (155 components) เท่านั้น** — ห้าม shadcn/Radix/MUI/อื่นๆ
   Tailwind v4 ใช้เก็บรายละเอียด layout ที่ Astryx ไม่มี prop เท่านั้น
2. สี/ระยะ/ตัวอักษรอ้าง **Astryx token** — ห้าม hex/px ดิบ; theme ปัจจุบัน `theme-neutral` (เปลี่ยน brand ผ่าน `astryx theme` ได้)
3. โครงหน้า: AppShell / Layout / SideNav ของ Astryx; ข้อมูลหนาแน่นใช้ Table/List edge-to-edge (ไม่ห่อ Card รายแถว); สถานะใช้ StatusDot/Token
4. ภาษาไทยเป็นหลัก · เวลาแสดงตาม timezone ก๊วน (default Asia/Bangkok)
5. Error message มาจาก error code กลาง (`docs/errors.md`) — ออกแบบ pattern การแสดง error/empty/loading ให้เป็นระบบเดียว
6. Realtime มีอยู่แล้วในหน้า roster — ออกแบบให้การเปลี่ยนแปลงสด (คนลงชื่อ/ยกเลิก/เลื่อนคิว) ไม่ทำให้ผู้ใช้งง

## 8. โจทย์ที่อยากได้จากการ redesign

1. **Information architecture ใหม่** — ตอนนี้เมนูในก๊วนมี 12+ หน้าแบน ๆ ควรจัดกลุ่ม (เล่น / เงิน / คน / ตั้งค่า) และแยก mental model ระหว่าง "โหมดสมาชิก" กับ "โหมดแอดมิน"
2. **Mobile-first ทุก flow หลัก** โดยเฉพาะ: ลงชื่อ (สมาชิก+guest), Game Console, สแกนเช็คอิน, จ่ายเงิน+สลิป, ตรวจสลิป
3. **หน้าแรกของก๊วนที่ตอบ "วันนี้ต้องทำอะไร"** — นัดถัดไป, ยอดค้างของฉัน, สิ่งที่ admin ต้องตรวจ
4. Flow guest ให้จบใน 1 หน้าจอ ไม่หลงว่าต้อง login
5. Visual identity ใหม่บน token ของ Astryx (สี brand, จังหวะ spacing, ภาพประกอบ)
6. ระบุ component Astryx ที่ใช้ต่อหน้า + จุดที่ต้องเขียน custom (ถ้ามี) เพื่อให้ dev agent ทำต่อได้ทันที

### User journeys หลักที่ต้องออกแบบ end-to-end
1. **สมาชิก:** เห็นแจ้งเตือนนัดใหม่ → ลงชื่อ → (เต็ม→waitlist→ได้เลื่อน) → โชว์ QR เช็คอิน → เล่น → เห็นยอด → จ่าย+ส่งสลิป → ผ่าน
2. **แอดมินวันจัดก๊วน:** เปิดนัดจาก template → รับลงชื่อ → สแกนเช็คอิน → จัดเกม+นับลูก → ปิดรอบ → ไล่ตรวจสลิป → ดูรายงาน
3. **Guest:** ได้ลิงก์ใน LINE → กรอกชื่อ+เบอร์ → เห็นสถานะ → จ่ายผ่าน QR → (ชวนสมัครเป็นสมาชิก)
4. **หัวหน้าก๊วนคนใหม่:** สมัคร → สร้างก๊วน → ตั้งราคา/ฝีมือ/flags → สร้างนัดแรก → ชวนคน (ลิงก์เชิญ/discovery)
